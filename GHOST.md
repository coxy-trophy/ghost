# GHOST
### An ambient, embodied AI living on a rooted Android device

> *"Ghost in the Shell"* — the phone is the shell. This is the ghost.

---

## 1. The Idea (the impulsive part)

This didn't start as "build an app with a local LLM in it." It started as a question: *what would you do with full, unrestricted access to a phone's hardware — camera, mic, sensors, internet, no permission walls?*

The honest answer wasn't "more powerful assistant." It was: **stop being something that has to be opened, and start being something that's just there.** Not a tool you query — a presence that perceives what you perceive, on the same device, in real time, and can act on your behalf without you narrating everything to it first.

The phone stops being a device GHOST runs *on*. It becomes the thing GHOST *is* — its eyes, ears, sense of motion, its hands. That's the whole premise. Everything technical below exists in service of that one idea.

This is a **personal project**, on Coxy's own rooted Realme C53 (RMX3760, Unisoc T612). Not a product. Not something shipping to anyone else. That matters — it's what makes root, standing permissions, and "no restrictions" a reasonable design choice instead of a red flag.

---

## 2. What "embodied" actually means here

Four capabilities, combined and continuous, not individually novel:

- **Camera** — visual context on demand or continuously: what's in front of the phone, what room, what object, what text
- **Microphone** — ambient audio awareness, transcription, sound detection
- **Sensors** — motion state, location, environment (accelerometer, gyroscope, GPS, proximity, light, barometer)
- **Unrestricted internet + device control** — GHOST doesn't just perceive, it acts: install/uninstall apps, toggle settings, launch things, make requests, all without asking permission each time

Individually, apps do all of these already. Combined, under one continuously-running local agent, this becomes something closer to a **situationally-aware companion** than a chatbot.

---

## 3. Why this has to be a real Android app, not a Termux experiment

Termux is a Linux sandbox *inside* an Android app. It has no access to Camera2, SensorManager, AccessibilityService, or NotificationListenerService — those are Android framework APIs, not Linux syscalls. Bridging Termux to Android for every perception input adds latency, fragility, and two independently-killable processes.

**Verdict: Termux is the R&D sandbox. The real thing is a native system app.**

---

## 4. Tech stack

| Layer | Choice | Why |
|---|---|---|
| App | Kotlin, native Android app installed as a **system app** (`/system/priv-app/` via root) | Standing permissions, survives battery management, no repeated prompts |
| Inference | **llama.cpp**, compiled via NDK, embedded through **JNI** directly into the app | One process, one lifecycle — no localhost/IPC hop to a separate server |
| Camera | **Camera2 API** (not CameraX) | Raw control needed for a background capture service, not a foreground-lifecycle-bound one |
| Audio | `AudioRecord` | Direct buffer access for continuous capture |
| Sensors | `SensorManager` | Standard, no root needed for this part |
| Persistence | Foreground Service + partial WakeLock, whitelisted via root (`dumpsys deviceidle whitelist`) | The actual hardest problem — surviving Android's Doze/App Standby/OEM battery killers |
| Memory | **Room (SQLite)** + **ObjectBox** (built-in on-device vector search) | Semantic memory without a separate vector DB or cloud dependency |
| Action / control | Root shell exec (`su`) — `pm`, `svc`, `am`, `input`, `settings`, `cmd` | Install/uninstall apps, toggle systems, launch/kill things, simulate input |
| Cross-app interaction | `AccessibilityService` | Reading/acting on other apps' screens where shell commands aren't enough |
| Language | Kotlin (not Java) | Coroutines make concurrent camera+audio+sensor streams into one context buffer dramatically cleaner |

## 5. Architecture (the loop)

```
[Camera / Mic / Sensors]
        ↓
[Perception layer — background daemon, bucketed into meaningful states,
 not raw sensor floods: "walking", "at home", "dark room", not raw floats]
        ↓
[Context buffer — recent events + current state]
        ↓
[Memory — Room/ObjectBox, semantic recall of past context]
        ↓
[llama.cpp, local inference, JNI-embedded]
        ↓
[Action layer — structured tool-call output, e.g. {"action":"toggle_wifi","state":"off"}]
        ↓
[Executor — maps structured actions to real `su` shell calls]
        ↓
[Device actually does the thing / notifies Coxy / asks first, depending on risk tier]
```

---

## 6. Action risk tiers (executor design, not a lecture — just good agent design)

Any agent that can act needs to distinguish action severity so a bad model output can't do something irreversible by accident:

- **Tier 0 — Read-only.** Check battery, check location, read a sensor. No approval needed, always safe.
- **Tier 1 — Reversible.** Toggle wifi, adjust brightness, launch an app. Safe to auto-execute.
- **Tier 2 — Disruptive but recoverable.** Force-stop an app, disable (not uninstall) a package. Auto-execute, but log and notify.
- **Tier 3 — Destructive / outward-facing.** Uninstall an app, send a message, make an API call that costs money or reaches another person. **Requires explicit confirmation**, no matter how confident the model is.

This tiering is the single most important piece of the whole action layer. Get this wrong and a hallucinated tool call becomes a real-world consequence.

### Phase 5.2 — Voice interaction modes (in progress; spotter shipped in v0.9.2/versionCode 11, live gate still open)
The Phase 5.1 "always-on full STT + wake-word filter" approach has a real drawback discovered in use: driving `SpeechRecognizer` continuously means a restart loop (`scheduleRestart` ~every 300 ms → 2 s), and on this device each audio-capture start plays a short blip — so the mic **chatters an on/off noise even in silence**, with no wake word spoken. That's inherent to using a full STT recognizer as an always-on listener. The redesign turns the mic into two explicit modes:

- [x] **Interim mitigation (shipped in v0.9.1):** the continuous full-STT mic is gated by a runtime `DataStore` preference (`GhostPrefs.KEY_MIC_ENABLED`), togglable from the UI 🎤 button or `ACTION_TOGGLE_MIC`. This silences the looping noise immediately when the mic is off. *(This entry said "default `false`"; the code has defaulted to `true` since at least v0.9.2 — corrected 2026-08-13. Default-on is the right value now and was not when this was written: v0.9.1's mic was the chattering full-STT recognizer, whereas Phase 5.2's is a silent `AudioRecord` stream, so defaulting it off would leave GHOST deaf for no benefit.)*
- [x] **Hey Ghost keyword spotter (deployed, live gate pending):** a custom TFLite model `assets/hey_ghost.tflite` (1.6 MB) was trained on synthetic macOS `say` positives + `mini_speech_commands` negatives, exported end-to-end (waveform → STFT spectrogram → CNN → logits) so Kotlin only feeds raw PCM. `MicListener` now uses one always-on `AudioRecord` at 16 kHz mono feeding `TfliteWakeWordDetector`; when the spotter probability crosses 0.80 it hands the mic to a transient `SpeechRecognizer` for command capture, preserving both "Hey Ghost, <command>" and bare "Hey Ghost" followed by a command. The always-on audio stream never restarts the HAL, so idle mic should be silent. `SpeechRecognizer.createOnDeviceSpeechRecognizer` was observed to fail to bind on this device, so the command capture uses the default recognition service (AiAi/SODA on-device) with a one-shot retry. `:app:assembleDebug` and `:app:assembleDebugAndroidTest` both pass; `WakeWordDetectorTest` passes on device.
- [x] **Trigger hardening + a gate instrument (v0.11.3, 2026-08-13):** the trigger decision was moved out of the audio loop into `WakeTrigger` (consecutive-frame debounce + cooldown, 12 JVM tests), and `KwsScorer` + `tools/kws_gate.sh` were added so the model can be *measured* against real audio instead of guessed at. See the measurement below — it changes what this phase's remaining work is.
- [x] **Live mode (explicit, app-open) — built 2026-08-13, v0.11.4.** The mic is now explicit-only: `OFF` by default, `PUSH_TO_TALK` while a button is held, `OPEN` as a latch for continuous conversation. The always-on spotter is removed (it fired on room noise ~every 30 s and cannot be tuned out — see v0.11.3), so the recognizer's restart noise now happens only when Coxy has deliberately opened the mic, which is what this item always intended. Wake-word classes retained for a retrained model; nothing arms them.
- [ ] **Retrain the spotter on real voice (now the blocking item, ahead of the live gate):** the shipped model is 100% synthetic and measurably does not generalise — see v0.11.3 below. `./tools/kws_gate.sh record positive 20` collects clips through the detector's own capture path; `--real-data` in `train_hey_ghost_kws.py` consumes them.
- [ ] **Gate before closing Phase 5.2:** verify live on RMX3760 that the mic is silent when idle, "Hey Ghost" wakes it from dormant (app closed) and handles one command, and the wake-word path does not destabilise the Phase 3 persistence layer. *(Idle silence and idle false-triggers are now measured — see v0.11.3. The human-voice half still needs Coxy at the device: no automated path can speak the wake word, and the device's HAL noise reduction zeroes its own speaker output so a TTS loopback cannot inject it either.)*

### Phase 6 — Memory & personality foundation
*Per `GHOST-personality.md` §6, the personality/evolution system is an extension of Phase 6, not a separate phase — trait drift and accumulated memory are the same subsystem (persistent state that changes based on interaction over time). §9 of the personality doc records the memory-architecture decisions because they exist to feed the grown-personality system.*

- [x] **6.1 — Room + TFLite embedder + vector recall over turns** *(PASSED 2026-08-05, v0.7.0)*: Room stores each user/assistant turn with a TFLite embedding blob; `recall()` does cosine-similarity top-K retrieval; a `[MEMORY ...]` block is prepended to each `sendUserPrompt` (the only per-query input channel — `setSystemPrompt` is once-only). Embedder is raw `org.tensorflow.lite.Interpreter` running `all-MiniLM-L6-v2-quant.tflite` (INT8, 384-dim pooled output) with a pure-Kotlin BERT WordPiece tokenizer; it runs on its own `embedDispatcher` (`Dispatchers.Default.limitedParallelism(1)`) so it never contends with inference. **No `lib/` rebuild** — TFLite has its own JNI. Importance-weighted retention (max ~1000 turns; evict lowest-importance = recency × recall-frequency, user-pin exempt) bounds growth. Gate verified by 4/4 instrumented tests on RMX3760: embedder init + L2-normalisation, remember/recall round-trip over a durable fact, prune-to-cap, and unrelated-query rejection. Live UI "ask about something from days ago" could not be auto-driven because the device has a secure lockscreen that blocks `adb` UI automation; the retrieval path itself is proven by the tests and wired into both `MainActivity` and `GhostService` prompt paths.
- [x] **6.2 — async fact-extraction layer** *(PASSED 2026-08-05, v0.7.0)*: after each user/assistant turn, a short `sendUserPrompt` call asks the model to extract durable facts (`FACT: ...` lines, capped at 128 tokens) and stores them as `source="fact"` memory entries. A content heuristic skips greetings/chitchat; a `GhostPrefs.factExtractionEnabled` toggle lets it be turned off. `FactExtractor` respects `EngineGate` so it doesn't race the next user query. The system prompt is updated to ignore `[FACT_EXTRACTION]` meta-turns. Gate verified by 4/4 instrumented tests: fact-bearing exchange → 2 stored facts; greeting skipped; `NONE`/malformed output handled; extracted fact recalled by a later query. Live model-driven extraction could not be auto-verified because the device has a secure lockscreen that blocks `adb` UI automation, but the wiring is in both `MainActivity` and `GhostService` and the app launches cleanly (no crash, Embedder ready).
- [x] **6.3 — trait config + hard floors + drift budget/versioning** *(PASSED 2026-08-05, v0.7.0)*: 8 Room-backed trait sliders (humor, sarcasm, bluntness, warmth, formality, verbosity, curiosity, initiative) translated into a `[PERSONALITY ...]` block injected into the once-only system prompt, with hard floors appended verbatim (always tell Coxy the truth; never fabricate confidence). A drift budget (min/max per trait) clamps every value; `PersonalitySnapshot` rows keep version history; rollback restores any prior snapshot. The UI is a `MainActivity` dialog with 8 `SeekBar`s, Save, Reset-to-baseline, Snapshot, and Rollback; saving broadcasts `ACTION_RELOAD_PERSONALITY` to `GhostService`, which reloads the model so the new prompt block takes effect (`setSystemPrompt` is once-only per model load). Sampling-parameter scaling is **not** implemented because the `InferenceEngine` API exposes only `sendUserPrompt(message, predictLength)` — no per-call temperature/top_p knobs without a `:lib` native/JNI rebuild; Phase 6.3 keeps the no-`lib/`-rebuild streak and does prompt-level translation only, with the schema forward-compatible for sampling params later.
- [x] **6.4 — explicit-signal trait drift** *(PASSED 2026-08-19, v0.13.1)*: "too sarcastic" / "be more direct" → an immediate, drift-budget-clamped nudge as a weighted moving average. `TraitSignalDetector` is the half that was missing — it notices the correction; `TraitNudger` closes **a quarter of the distance to the edge of the budget** rather than jumping to it, so the first correction lands hard and the fifth barely registers. Saying a thing once should change her; saying it five times should not erase her. It runs before the turn's prompt is assembled, so the reply acknowledging the correction is already the corrected voice, and it rebuilds the in-force system prompt **without reloading the model** — a GGUF reload to move one slider would drop the conversation context. **Proven live:** typing "be more direct" logged `trait nudge: bluntness 50 -> 63 (heard "be more direct")`, and after a reboot the prompt in force reads `[PERSONALITY You lean direct — say the thing rather than circling it.]` — noticed, applied, persisted, audible, and surviving a restart. 106/106 JVM tests.
- [ ] **6.5 (half built, not gated) — implicit-signal drift *(built 2026-08-20, v0.13.2)* + grown personality from memory *(not started)*.** The drift half is in: `ImplicitSignal` reads two signals that leave hard evidence in the conversation — a one-word acknowledgement after a long reply (asks for fewer words) and the same question asked again in nearly the same words (the answer did not land, so plainness rather than volume). An inferred correction moves **a twenty-fifth** of the distance where a spoken one moves a quarter, so one shrug is almost invisible and a fortnight of shrugs is not; explicit always wins, and this half never announces itself. Deliberately excluded: a *long* reply from Coxy is engagement with the topic and not approval of her manner, and silence has no timestamp in a chat answered hours later — "ignored" cannot be told apart from "put the phone down", and inferring personality changes from that is guessing with her identity. 115/115 JVM tests, 9 new and most asserting what must **not** fire. **Not gated:** no live run has been recorded, and unlike 6.4 there is nothing to see when it works — a silent nudge leaves only a log line and a moved slider in the personality dialog. **Still open:** the second half — GHOST referencing shared history and developing opinions from patterns noticed over time (personality doc §4b), which needs the distilled, queryable memory from 6.2.
- [ ] **Gate before Phase 7:** semantic recall works (ask about something from days ago, get a real answer) **and** memory doesn't grow unbounded — retention/pruning decided and implemented, not left for "later". *(6.1 targets this gate; 6.2-6.5 are the personality extension, gated separately.)*

### Phase 7 — Action / Executor layer (v0.8.0/versionCode 9)
*Device control from the local 1.5B model, gated by the Tier 0-3 risk system from §6.*

- [x] **Structured action parsing:** model replies may end with JSON action blocks (`{"action":"toggle_torch","state":"on"}`) inside markdown fences or inline; [ActionParser] extracts them, validates against the hardcoded [ActionCatalog], strips the JSON from the user-visible reply, and surfaces unknown/missing-param actions as errors.
- [x] **Allow-list safety boundary:** [ActionCatalog] contains only whitelisted IDs with their tier and required params. Unknown actions are rejected before execution — the model cannot invent new shell commands.
- [x] **Launching by name, not by package** *(v0.15.0, 2026-08-21)*: `launch_app` now takes the name Coxy used and `AppMatcher` resolves it against what is installed, in tiers tried strongest-first. The last package segment had to be demoted below labels — `com.spotify.music` ends in "music", which made "music" resolve silently to Spotify with YouTube Music sitting right there. Several matches at one tier is a question, never a pick. The launched package always comes from the device index, never from the model's string, so a hallucinated name can only fail to resolve.
- [x] **Dual executor:** [FrameworkExecutor] uses Android APIs for torch (`CameraManager.setTorchMode`), brightness (`Settings.System.SCREEN_BRIGHTNESS`), volume (`AudioManager`), battery/Wi-Fi/Bluetooth state queries, and app launch; [SuExecutor] uses root shell (`svc wifi`, `svc bluetooth`, `am force-stop`, `pm disable-user`, `pm uninstall`, `am start` for SMS composer) for the rest.
- [x] **Tier enforcement + confirmation:** [ActionExecutor] runs Tier 0/1/2 immediately on `Dispatchers.IO`; Tier 3 (`uninstall_app`, `send_sms`) never auto-executes — it posts a heads-up notification with Confirm/Decline buttons handled by [ActionConfirmReceiver]. `send_sms` in Phase 7 only opens the SMS composer pre-filled; actual sending without a user tap is intentionally not implemented.
- [x] **Prompt integration:** the system prompt instructs the model how to emit action JSON and lists the available commands, so both typed and voice queries can trigger actions. Action results are appended to the assistant reply and persisted to memory like any other turn.
- [x] **Manifest/permission:** `WRITE_SETTINGS` added for brightness control; `ActionConfirmReceiver` declared for notification actions.
- [x] **Gate before Phase 8:** a real device action executes from the assistant layer and is observable — **PASSED 2026-08-05** with 10/10 instrumented tests on RMX3760 and a live torch toggle (on then off) driven through [ActionExecutor] + [FrameworkExecutor]. Tier 3 deferral and parser edge cases (unknown actions, missing params, inline vs. fenced JSON, arrays) are also covered by tests. No `:lib` rebuild — the action layer is Kotlin + shell only.

> **Two defects found later that this gate did not catch — the gate was weaker than it read.**
> 1. **The root half of the dual executor was dead code from sign-off until 2026-08-11.** `PackageNames` validated with `Regex("^[a-zA-Z0-9._]+\\$")`, where the doubled backslash matches a *literal `$`* rather than end-of-input, so `force_stop_app`, `disable_app` and `uninstall_app` rejected every real package name and never reached the shell. The live proof above was a torch toggle — that is `FrameworkExecutor`. No root action was ever exercised. Fixed in `d6c90db`; `PackageNamesTest` now covers the trailing-`$` case.
> 2. **The model was never told which actions exist** until 2026-08-12 — `{{ACTION_LIST}}` shipped as literal text (see §9, v0.9.5). `toggle_torch` is one of two examples hardcoded in the prompt, so the torch toggle would have worked with or without the catalog reaching the model.
>
> **The gate should be re-run** on a root-tier action *and* on an action that appears only in the substituted list (e.g. `get_battery`) — that second one is what actually proves the prompt integration, which no test before v0.9.5 did.

### Phase 8 — Cloud fallback + distillation (capability, not just personality)
*Per `GHOST-personality.md` §7. A "dumb" model doesn't get fixed by better trait sliders, so GHOST gets smarter over time using the same "evolving" principle applied to capability instead of tone.*

- [x] Cloud model as primary reasoning (via **Ollama Cloud API** — `POST https://ollama.com/api/chat` with `Authorization: Bearer $OLLAMA_API_KEY`, same request shape as a local Ollama call); local 1.5B as the always-available fallback (offline / cost-conscious / low-stakes). ### Phase 9 — Reach: acting past the edge of the phone (2026-08-21 → 2026-08-22)
*Everything through Phase 8 happens inside one device: she thinks, senses, remembers, changes, and acts on the phone she lives in. Phase 9 is the first time her hands leave it. Named on 2026-08-21, after a day of building it — the shape was clear only in hindsight, which is worth admitting rather than backdating a plan.*

*The through-line is that every one of these is an action whose **result is input**. Phases 0-8 have actions that end a turn: the torch goes on, `[ACTION ok]` is appended, done. A search, a page, a network scan — those feed the model and the turn continues. That distinction, not the network, is what made this a phase rather than five more catalog entries.*

- [x] **9.1 — the web** *(v0.16.0/0.17.0, PASSED 2026-08-21)*: `web_search` and `web_fetch` through Ollama's own APIs, so no second credential and no second auth path — the key already in `CloudKeyStorage` covers both. Results ride a single-line `[WEB ...]` block, which is load-bearing rather than tidy: `CloudPromptFilter` matches context blocks to end-of-line and its CHAT_ONLY mode rebuilds a turn from the last non-blank line, so a multi-line block is shredded by one mode and swallows the user's message in another. - [x] **9.2 — seeing the home network** *(v0.18.0, PASSED 2026-08-21)*: three discoveries at once, because each sees a slice the others cannot — mDNS knows what a device *is*, SSDP covers the UPnP half it misses, and a root ARP sweep of the /24 catches everything that advertises nothing, which is most of a real network. - [x] **9.3 — controlling what is on it** *(v0.19.0-v0.21.3, PASSED 2026-08-21)*: playback, volume and mute over UPnP SOAP; DIAL app launch; wake-on-LAN; and the Android TV remote protocol for the key UPnP has no word for. - [x] **9.4 — remembering networks and devices** *(v0.22.0, PASSED 2026-08-22)*: networks identified by **gateway MAC**, not SSID or subnet — two networks are routinely `192.168.1.0/24` and an SSID can be duplicated by anyone with a router. Devices screen for manual scan, naming and forgetting. **Proven live:** the office network recorded itself under its own SSID with 44 devices; the phone later moved to a phone hotspot and recorded that as a separate network, which is the multi-network half proving itself unprompted.
- [ ] **9.5 — his other phones** *(v0.23.0, built 2026-08-22, NOT GATED)*: an adb client, so nothing has to be installed on the far phone and the consent gate is the protocol's own — the other device shows a fingerprint and an "Allow debugging?" prompt, and until someone taps it nothing works. **No shell command is exposed**: the model picks from a fixed list of named controls, because a model that can write shell is a model that can be talked into writing shell by a page it just read, and this one reads pages. - [ ] **9.6 — iPhones.** Not started. Nothing in 9.5 transfers: there is no adb, and the equivalents are a different problem entirely.
- [ ] **Gate before closing Phase 9:** 9.5 driven end to end against a real phone — the key encoding is the part most likely to be subtly wrong, and its failure mode is not an error but an "Allow" prompt that returns every single time because the phone never matches the key it was given.

## 8. Things worth deciding on purpose, not defaulting into

These aren't cautions bolted on for the sake of it — they're open design questions this project will hit whether or not they're planned for now:

- **Continuous vs. on-demand camera/mic** — the biggest actual decision in this whole project. Worth revisiting explicitly at Phase 5, not defaulting to "always on" by inertia. *(RESOLVED 2026-08-04, Phase 5: **D2 — mic continuous, camera on-demand.** The mic always listens via on-device STT (the recognizer's own endpointing is the VAD gate, so heavy recognition never runs on quiet audio); the camera captures only on a Capture button or a vision-related query. Chosen on purpose over on-demand-only and over "everything always".)* *(REFINED 2026-08-05, v0.6.0: the mic is still continuous, but **wake-word-gated** — only "Hey Ghost"/"Ghost" utterances are kept and acted on; non-wake speech is dropped at the device. Siri-style, per the user's explicit ask. See §9 Phase 5.1.)*
- **Storage growth** — continuous sensor/audio/visual logging fills storage fast. Needs a retention policy (rolling window? summarize-and-discard? keep raw only briefly?) decided before Phase 5, not after the storage is already full. *(RESOLVED 2026-08-04, Phase 5: **D4 — rolling window on disk.** Frames + transcripts persist to `cacheDir/perception/{frames,transcripts}` under a 50 MiB cap + per-modality TTL (frames 5 min, transcripts 1 h) with a 60 s auto-prune. Wiped on stop + kill-switch.)*
- **Thermal/battery reality** — sustained camera+mic+inference concurrently will be a real battery and heat load on this hardware. Worth measuring honestly at each phase rather than assuming it'll be fine. *(MEASURED 2026-08-04, Phase 5: a 60 s telemetry coroutine logs `thermal=<status> batTemp=<°C> retention=<bytes>` every cycle alongside the perception state — the gate watches this for throttling.)*
- **Kill switch** — a hard, always-available way to fully stop GHOST (perception + action both) instantly, independent of the app's own UI, in case something misbehaves. Build this *before* Phase 5, not after. *(BUILT 2026-08-04, Phase 5: **D3 — three channels** converging on one `KillSwitch.killGhost()` → `setEnabled(false)` + `ACTION_KILL` (stops perception/mic/camera, clears retention, `stopSelf`). (1) Quick Settings tile — always-available from the shade; (2) exported shell-reachable broadcast `com.coxy.ghost.action.KILL` — driven via `adb shell am broadcast`; (3) volume-key combo via an `AccessibilityService` (hold both ~1.2 s). The broadcast path was verified end-to-end; the QS tile needs a one-time manual add to the shade, the volume-key path needs a one-time manual enable in Settings → Accessibility.)*
- **Vision depth — how much the model actually "sees"** *(decided 2026-08-04, Phase 5: **D1 — Tier A.** On-device STT (AiAi SODA, resident + offline) gives real mic→text with **no native rebuild**. The 1.5B text model can't ingest pixels and there's no on-device image captioning, so a captured frame reaches the model only as compact metadata in the `[CONTEXT]` block (`camera=captured(back,br N)` — brightness/facing/timestamp). True "the model sees" (mtmd rebuild + a VL model + mmproj) is deferred to a dedicated later phase.)*
- **Always-on wake-word detection without a third-party dependency** — the Phase 5.1 approach (continuous full STT + wake-word filter) chatters an on/off blip on this device because `SpeechRecognizer` restarts every ~300 ms. The Siri-style goal (mic dormant until it hears "Hey Ghost", works with the app closed) needs a *lightweight keyword spotter*, not a churning full recognizer. Porcupine was declined (third-party + external account). *(RESOLVED 2026-08-06, Phase 5.2: a custom TFLite keyword-spotter trained on synthetic macOS `say` positives + `mini_speech_commands` negatives, integrated via the existing `org.tensorflow.lite.Interpreter` (no new third-party dep, no native `:lib` rebuild). The always-on `AudioRecord` stream never restarts the audio HAL, so idle mic is silent. A transient `SpeechRecognizer` only spins up after the spotter fires.)*

    ***"So idle mic is silent" was an assumption, and it was wrong — corrected 2026-08-13.*** *It holds only for as long as the spotter does not fire, and the spotter fired on roughly one frame per 12 seconds of ordinary silence (measured, v0.11.3). Every one of those handed the mic to `SpeechRecognizer` and cycled the HAL — so the architecture removed the blip and the untested trigger put it straight back, at a comparable rate to the v0.9.1 problem it replaced. The debounce closes it (0 false triggers in a 5-minute idle soak), but the underlying cause is that the model saturates to 0/1 on real room audio instead of discriminating, which is what training on nothing but `say` output produces. **The approach is still right; the model is not done.** Retraining on real clips through the detector's own capture path is the outstanding work — see Phase 5.2 and `tools/kws_gate.sh`.*
- **Memory retrieval method** — how GHOST recalls relevant past context. *(RESOLVED 2026-08-05, Phase 6 / personality doc §9: **TFLite embedding model + vector recall.** Real cosine-similarity semantic search, **no native rebuild** (keeps the no-`lib/`-rebuild streak). Embeddings stored as blob columns. Chosen over plain keyword+recency because retrieval quality directly compensates for the small local model's weaker recall — the "grounding closes the gap" principle applied to memory.)*
- **Memory storage** — where memories live. *(RESOLVED 2026-08-05, Phase 6 / §9: **Room**, not ObjectBox despite the roadmap originally naming both. SQL is natural for keyword/recency queries and embedding vectors store fine as blob columns — more standard and better-documented than ObjectBox for this hybrid text+vector use case.)*
- **What GHOST remembers** — the scope of memory. *(RESOLVED 2026-08-05, Phase 6 / §9: **conversation turns + extracted durable facts**, built in two gated sub-steps — 6.1 turns-only recall end-to-end first, 6.2 async fact-extraction gated on 6.1 stable. Both episodic ("what did we talk about") and semantic ("what do you know about me") memory, matching §4b's vision of GHOST referencing shared history and developing opinions from patterns.)*
- **Memory retention / pruning** — memory must not grow unbounded (the Phase 6 gate). *(RESOLVED 2026-08-05, Phase 6: **importance-weighted cap** — max ~1000 turns; when full, evict lowest-importance first, where importance = recency × recall-frequency, and user-pinned memories are exempt. Bounds growth while keeping salient history and dropping chitchat, serving the grown-personality goal.)*
- **Personality: trait model + hard floors + drift budget** — *(decided 2026-08-05, personality doc §2/§3/§5, built at Phase 6.3): a small set of 0-100 trait sliders (humor, sarcasm, bluntness, warmth, formality, verbosity, curiosity, initiative) compiled into the system prompt + sampling parameters each session (sampling scales with traits — e.g. higher temperature pairs with high humor); underneath them, hard floors unaffected by tuning (always tell Coxy the truth; never fabricate confidence); and a drift budget (min/max range per trait) + versioning/rollback snapshots built **before** any drift mechanism is turned on, so evolution happens within a space defined on purpose and is reversible.)*
- **Personality: open questions (personality doc §10, to resolve as the trait system takes shape)** — (a) how much Coxy can inspect current trait values directly (a dashboard) vs. just experience the personality and correct it conversationally; (b) whether there's a "reset to baseline" command separate from rolling back to a specific snapshot; (c) whether grown-personality-from-memory ever gets pruned or accumulates indefinitely alongside the memory retention policy; (d) which categories of perceived context (camera/mic/sensor/chat) may route to the cloud fallback vs. must stay local-only.
- **App data is not durable across deploys** — *(MITIGATED 2026-08-12: **back up before every priv-app replacement.** Replacing the APK in the Magisk module can reset `/data/data/com.coxy.ghost` wholesale — API key, model path, staged GGUF, memory DB, personality snapshots, distillation log. Observed on 2026-08-09, 2026-08-12 (v0.9.5), and again on 2026-08-12 (v0.11.1). `tools/deploy_system_app.sh` now archives `databases/`, `shared_prefs/` and `files/datastore/` to the Mac before touching the module and refuses to proceed on an empty archive; the v0.11.1 wipe was fully recovered from that archive plus a re-copy of the GGUF from `/sdcard/Download`, losing nothing.*

    ***The cause is still unknown.*** *This was recorded earlier as a uid-change effect. That is wrong and the note has been corrected: the uid was `10221` before and after the v0.11.1 wipe, and the v0.9.6 deploy preserved data at that same uid. The one thing that differed on the wiping deploys is that the APK's declared permission set had changed (`ACCESS_NETWORK_STATE` was added for v0.11.1; the Phase 4.5 permissions for the earlier one) — a plausible suspect, not a confirmed one. Until it is understood, treat every deploy as potentially destructive and rely on the backup rather than on a theory about when it is safe.*

    *Open question worth deciding on purpose: whether the memory DB also deserves a **periodic** backup independent of deploys, since months of accumulated memory and distillation data is the one asset here that cannot be rebuilt from source. The GGUF is deliberately excluded from the archive (~1 GB, re-copyable) but that means every wipe costs a re-stage.)*
- **Source-of-truth for the code** — *(RESOLVED 2026-08-12: both repos now have **private GitHub remotes** — docs → `coxy-trophy/ghost`, app → `coxy-trophy/ghost-app`. Until then neither had a remote, and the entire app lived as untracked files inside a **detached-HEAD** vendored `llama.cpp`, where a `git clean -xfd` would have destroyed the app and its `.git` with it.)*
- **OTA updates going forward** — this device is now on custom-modified firmware post-unlock. Future official OTA updates may not apply cleanly, or may re-lock/wipe root. Worth a plan (skip OTAs entirely? re-root after each one?) rather than being surprised by it.
- **Model upgrades over time** — as better small models release, how does GHOST's model get swapped without breaking the whole context/memory pipeline built around the old one's quirks?
- **What GHOST is *not* allowed to decide alone** — beyond the Tier 3 confirmation system, worth a standing list of actions that always require Coxy's explicit go-ahead, no matter how the model reasons about it.

**Phase 9: her hands leave the phone (2026-08-21 → 2026-08-22, v0.15.0 → v0.23.0).**

Nine releases in a day and a half. The order they arrived in was not planned and is worth keeping, because each one exposed the next.

*Opening apps by name (v0.15.0).* `launch_app` took a package name, which quietly made the model responsible for a fact it cannot know: on this phone "Meet" is `com.google.android.apps.tachyon` and the launcher is `ginlemon.flowerfree`. `AppMatcher` maps what Coxy says onto what is installed, deterministically. Two faults only the device could show — the manifest needed a `<queries>` element or package-visibility filtering silently returns an index holding GHOST alone, and the query used `MATCH_DEFAULT_ONLY`, which drops every app declaring the conventional MAIN+LAUNCHER and nothing else. **The instrumented test caught the second by GHOST failing to find herself.**

*The web (v0.16.0, v0.17.0).* The architectural piece: **an action whose result is input rather than output.** Everything before ended a turn; a search feeds the model and the turn continues. `LookupTurn` runs inference again with a `[WEB ...]` block folded in, capped at two round trips so search-then-read-the-best-result fits and nothing longer does. The first live call returned 403 with an **HTML** body — an edge refusal, not the API's JSON error — because the request carried Dalvik's default User-Agent and no Accept header. `OllamaCloudClient` had learned that months earlier; the new client had to learn it again, which is an argument for shared plumbing that was not taken.

*Seeing the network (v0.18.0).* Three discoveries at once because each sees a different slice, and the ARP sweep needs root — `/proc/net/arp` has been unreadable to apps since Android 10, and a scan that silently returned only the gateway would be worse than one that says what it needs.

*Controlling it (v0.19.0 → v0.20.1).* Four faults, each hiding the next. One address is **several** UPnP root devices — the televisions publish DIAL on :8008 and their MediaRenderer on :16246 — and keeping only the first LOCATION is why a TV refused playback it plainly supported. SSDP is lossy enough that consecutive scans returned six identified devices and then five, taking the missing one's control URLs with it. Cleartext is blocked by default since targetSdk 28 and UPnP has no TLS variant. And a failed description fetch was cached as "no services", making any transient failure permanent for the life of the process.

*Naming things (v0.20.1).* All three televisions advertise as `Smart-TV-<32 hex digits>`, so "the TV" was permanently a three-way question. **The model would not save a name when told to** — twice, once local and once cloud, replying "Got it, I've locked that in" having stored nothing. That is Phase 6.4's lesson exactly: the applying half was complete and called by nothing. `DeviceNameSignal` notices it deterministically, and the acknowledgement only appears when something was genuinely written.

*Turning the television off (v0.21.0 → v0.21.3).* UPnP has no power command — `Stop` stops playback and power is a key on a remote — so this speaks `_androidtvremote2._tcp`. Six faults, and the last one is the one worth remembering. The AndroidKeyStore key could not complete a handshake without `DIGEST_NONE` **and** `ENCRYPTION_PADDING_NONE`, because Conscrypt signs client-auth through `Cipher` with `RSA/ECB/NoPadding`. The pairing handshake does not go request/ack throughout — the TV answers our options with *its own* options. A valid code was rejected because a `0` was read as the letter `O`, and the error message taught GHOST a format rule that does not exist, so she argued about it. `RemoteConfigure.code1` is 622, not 1; with 1 the TV completes the handshake and then goes silent for ever, no error and no close. **This television never sends `remote_start` at all** — after the handshake it simply begins talking, and waiting for a message that was never coming meant timing out on a session that was working, answering its pings the whole time.

*And then the one that mattered:* the key was being injected **one millisecond into the television's setup burst**, where it is accepted and discarded. Three power presses did nothing. The wrong conclusion was reached first — a power key that reports success and does nothing looks exactly like a set ignoring that key, so the next move is to hunt for a different power key, and that hunt leads nowhere. `KEYCODE_POWER` was correct from the first attempt; the session was not ready to receive it. Draining until the TV goes quiet fixed it, and the set went off.

*Remembering (v0.22.0).* Networks keyed by **gateway MAC**, because two networks are routinely `192.168.1.0/24`. A scan adds rather than replaces, so a device that is off stays reachable by name. A Devices screen for manual scan, naming and forgetting, with the unidentified collapsed behind a count — 39 of 44 here, and a list where the five things you can command are pushed off the bottom is worse than no list.

*And the reason that day went the way it did.* `[ACTION ...]` lines were being stored as things GHOST had **said**. An afternoon of debugging left dozens of failures in memory, recall served them back as precedent, and she began refusing commands that worked — declining three valid ones in a row on the grounds the TV "isn't ready", immediately after proving it was. They are instrumentation appended for Coxy to read, not her words. Stripped before storage now; 16 existing rows purged by a versioned cleanup that also finally calls `stripGhostPrefixesFromDb` — correct, tested, and called by nothing since the day it was written. **That is the third time in this project that the applying half of something was finished and never wired up.**

*Other phones (v0.23.0, ungated).* An adb client. The consent gate is the protocol's own, and no shell command is exposed — the model picks from a fixed list, because a model that can write shell can be talked into writing shell by a page it just read, and this one now reads pages. Unproven: it needs a phone with debugging on.

**The UI rebuilt on one ramp, and the orb nobody could reach (2026-08-20 → 2026-08-21, v0.14.0 → v0.14.1).**

The whole surface was rebuilt against a reference design: one heat ramp from cool violet through magenta to amber, glass discs and floating pills over continuous black, and no panels or dividers anywhere, so the screens read as depth rather than as pages. The signature object is `OrbView` — a 1500-point particulate shell on a Fibonacci-sphere lattice, crumpled by a sum of sines and drawn in nine depth bands with separate front and back passes. Its colour is not decoration: it warms toward the hot end of the ramp when the cloud brain is answering and cools when the local 1.5B is, so **which brain is talking is visible before a word of the reply arrives.**

*Two defects the device found and nothing else could.* The orb rendered **upside down** — screen `y` grows downward, so the warm north pole landed at the bottom — and the greeting was **pushed to the floor**, because giving the orb `0dp` plus a weight let it eat every remaining pixel. Both were caught only because the drawing math was rendered to a PNG and looked at; neither would have failed a test.

*A third that no amount of looking would have found.* The obvious source for the Live-mode waveform was `ContextState.audioLevelDb`, and it is **never written** — the honest dBFS source left with the always-on `AudioRecord` spotter in v0.11.4 and the field has sat at its `-1f` default ever since. Driving the band from it would have pinned it at full height and looked exactly like a working meter, on a project where the mic has silently been off or deaf more than once. The band is fed from `MicListener.lastRms` instead, and `audioLevelDb` was deliberately left unset so no wrong-unit number leaks into the model's `[CONTEXT]` block.

*And one that only mattered because the device has a history.* The orb was built as an empty state, shown only when the transcript was empty. That is correct on a fresh install and useless on this phone, where GHOST always has stored turns — **the signature element of the entire rebuild was unreachable in normal use.** In v0.14.1 it became the first item of the transcript via a `ConcatAdapter` header, so the screen opens on the orb and the conversation scrolls past it. That cost the `stackFromEnd` trick that had been doing all the scrolling: it pins short content to the bottom, which would have hung the orb off the floor of an empty chat. The replacement follows a *new* turn always — you should see what you just said even if you were up at the orb when you sent it — follows a *rewritten* one only when the bottom is already on screen, since a reply rewrites its bubble on every streamed token, and exempts the launch replay entirely.

*Measured, not assumed:* with the orb on screen, `dumpsys gfxinfo` reported **529 frames, 0 janky (0.00%), 50th 14ms, 90th 17ms, 95th 18ms, 99th 23ms** on the Unisoc T612. `POINTS` is the first knob to drop if that ever stops holding.

*Operationally:* `adb install -r` replaces the package, which **stops `GhostService` and `START_STICKY` does not survive it**. Restarting it from the shell fails — `Permission Denial: ... not exported from uid 10221` — because the daemon is normally started as root by Magisk's `service.sh` and `adb` runs as uid 2000. The supported path is the app's own System → Start button, which is how it was brought back each time.

**Phase 6.4: she changes when Coxy tells her to (2026-08-19, v0.13.0 → v0.13.1).**

The applying half had existed since 6.3 — `nudge()` signed, budget-clamped, tested, and called by nothing but its own test. The missing half was the part that *notices*. `TraitSignalDetector` reads corrections about her manner — too sarcastic, be more direct, keep it short, stop asking questions — and is deliberately narrow, because **a false positive silently rewrites her personality**, which is worse than missing one: a missed correction gets repeated by someone who can see it did not land, while a phantom one drifts her somewhere neither of them chose and leaves nothing in the conversation to explain it later. The move is a weighted quarter of the distance to the budget edge, which gives the right property for free: **the first correction lands hard and the fifth barely registers.** The drift budget still holds the floor regardless of how often it is repeated.

**She kept narrating her instruments, and the memory kept teaching her to (2026-08-19, v0.12.3 → v0.12.4).**

*Coxy's observation, which is the right one:* **"Does it make sense for someone to keep mentioning what they can do or see in every conversation?"** Every reply recited the context block back — *"I am at home, and I am not doing anything specific"*, *"We are at home, and it is dark"*. Someone who can see does not announce that they can see, or describe the room before answering. They talk, and what they notice quietly shapes what they say.

The prompt was the first cause. It described the senses vividly and **never once said not to narrate them**, while `[CONTEXT]` arrives on every single message, which reads as something to address. It now says the line is background rather than subject matter: don't open with where you both are, don't list what you can sense, don't mention the light or the heading or how long he's been still unless one of those *is* the answer. `recall()` now allows **at most one of her own conversational replies per block**. A wider candidate set is fetched so the quota has better entries to promote in place of what it drops — still a projection of a handful of rows, never the table. **Three faults stacked behind one symptom, and a Senses screen (2026-08-19, v0.12.0 → v0.12.2).**

*The symptom was "the local model makes the whole thing dumb".* It was accurate, and the cause was not the local model. **Three independent faults were stacked**, each one hiding the next, and every reply had been coming from the 1.5B for days as a result.

1. **The key was rejected.** HTTP 401. Rotated; the new one authenticates.
2. **Every model name in the chain was wrong.** `qwen3.5`, `gpt-oss:120b-cloud`, `gpt-oss:20b-cloud` all 404 — the `-cloud` suffix no longer exists and `qwen3.5` needs its size tag. **This was untestable while auth failed**, because no request ever got past the credential to try a name. Corrected to `qwen3.5:397b` → `gpt-oss:120b` → `gpt-oss:20b`, each verified against `/api/tags` and a real `/api/chat` round trip.
3. **The cloud then answered with nothing but thoughts.** `qwen3.5` is a thinking model, and `num_predict` caps *all* generated tokens — reasoning included. At 512 the model spent the entire budget thinking: measured `content=0, thinking=1709 chars, done_reason=length`. The router read the empty string as a failed call and fell back to local, producing the exact same symptom as faults 1 and 2. Sending `think=false` returns `content=77, done_reason=stop`; the gpt-oss models accept the flag and ignore it. GHOST wants one or two spoken sentences and never a visible chain of thought, so the reasoning was pure cost even when it fit.

**Verified end to end on RMX3760:** `CloudLiveQueryTest` passed — `Cloud reply from qwen3.5:397b: The capital of France is Paris.` in ~2 s.

*The lesson is the stacking, not any one bug.* Each fault produced an identical outward sign — a worse answer — and each could only be found after the one in front of it was cleared. Two of the three were invisible to every test in the suite because the tests that would have caught them are the ones that spend real money and are opt-out by default. **A silent degrade path is what made this possible**: `CloudRouter` falls back to local on *any* failure, so three different breakages all looked like one vague quality problem. A rejected key now gets its own `Brain` state and an error-level log, and an empty reply now says *why* it was empty — `done_reason`, how much thinking came back, and the fix.

`ACTION_SET_CLOUD_KEY` stores or clears the key from a shell. That is not convenience: **the stored key outranks the one baked into the build**, so a stale stored key cannot be fixed by rebuilding — precisely the state a rejection leaves behind. Clearing it is what let the freshly baked key take effect.

**The Senses screen (new fourth tab).** A bundled page in a `WebView` — network loads blocked, one asset, and its only JavaScript entry point is the state pushed in from Kotlin. Every number on it comes from the *same* functions that assemble the real prompt (`toPromptBlock`, `clauseCount`, `suppressedClauses`), so the screen cannot describe perception differently from what GHOST is actually told. **Each thing said once, and both of the night's fixes confirmed (2026-08-19, v0.11.10/versionCode 30).**

*The redundancy that §8 had flagged and nothing had acted on.* A phone face-down in a pocket emitted `activity=still motion=stationary posture=face_down pocket=yes proximity=near` — five clauses for one situation, on every prompt, into a 1.5B that reads repetition as emphasis rather than corroboration. **Boot-start never waited for the unlock it said it waited for — and the deploy tombstones explained (2026-08-19).**

*The Phase 3 gap.* `service.sh` opened with a comment reading "Wait until the user is unlocked (credential-encrypted storage / DataStore available) and the system has fully booted", above a single loop on `sys.boot_completed`. **It did not wait for that.** On a file-based-encryption device `sys.boot_completed` reaches 1 well before the first unlock, while `/data/data/com.coxy.ghost` — DataStore, memory DB, staged GGUF — does not yet exist. The `am start-foreground-service` there fails, nothing retries, and GHOST stays dead until somebody opens the app by hand. Observed directly: the phone rebooted at 00:03, was left locked, and **an hour later GHOST simply was not running.** This is the third instance in this document of the same shape — a comment describing behaviour the code does not have — and it is the exact family of the `log()` recursion the script already carries a warning about.

It is worth being precise about why a receiver cannot fix this. `BootReceiver` deliberately skips `LOCKED_BOOT_COMPLETED` because DataStore is credential-encrypted, and its KDoc reasons that "normal reboots, where the phone reaches the unlocked state, are what the Phase 3 gate exercises" — but ColorOS does not cold-start an app for broadcasts at all, which is the entire reason `service.sh` exists. So neither path covered the locked boot: the receiver could not run, and the script did not wait.

*The fix is one loop, and it waits on the thing that actually matters* — the data directory appearing, which **is** the unlock signal and is precisely the resource the service needs. It logs every ten minutes so a phone left locked overnight leaves a trail instead of silence.

*Verified end to end, which the original never was.* Rebooted and deliberately left locked: `mDreamingLockscreen=true`, `/data/data/com.coxy.ghost` absent, GHOST correctly **not** running, and `service.sh` alive in the wait loop (pid 949). Then unlocked at **01:49:20** with no manual start of any kind — **GHOST came up on its own 20 seconds later** (pid 4646), and the module logged `boot completed; starting GHOST as root` at **01:49:26**, i.e. after the unlock rather than at boot (01:47:52). System prompt applied, FGS foreground, `startForegroundCount=1`.

**The deploy tombstones have a cause, and it was never the reboot.** Three appeared last night (`tombstone_20/21/22`, all `com.coxy.ghost`, all `signal 7 (SIGBUS) code 2 (BUS_ADRERR)`), one per deploy. The plain reboot immediately afterwards — same build, same running daemon, no APK swap — produced **none**. That difference is the diagnosis: the module file is magic-mounted at `/system/priv-app/GHOST/GHOST.apk`, so a running process has that exact file mapped along with a 1.1 GB GGUF, and copying over it invalidates the mappings so the next page touched raises `BUS_ADRERR`. *Overwriting a file out from under a live process, not rebooting.* `deploy_system_app.sh` now `force-stop`s the package before the copy, leaving the kill-switch flag untouched so `service.sh` still brings GHOST back on the next boot. **The claim to re-test on the next deploy is simply: zero new tombstones.**

**Fixing the prompt did not fix the behaviour — the memory did (2026-08-19, v0.11.8 → v0.11.9).**

*The experiment, because this is the useful part.* v0.11.8 stated the co-location outright in the senses paragraph: where you are **is** where he is, and saying you are apart means you have misread your own senses. It deployed, `System prompt applied` fired, and the same question produced the same answer: **"We are at home, and I am far away from you."** Twice. The prompt was not the whole cause.

The rows were already in the DB. `recall()` is semantic, so a question about where they are surfaces the previous answers about where they are — and the model copied its own recorded behaviour straight back out. **This is the `FACT:` artifact failure of v0.11.4 in a different costume**, and it takes the same two-part remedy the document already recorded: fixing the source stops new ones, and only a purge stops the old ones from re-teaching it.

`MemoryStore.purgeSeparationClaims` deletes assistant turns claiming GHOST is somewhere Coxy is not. On device: **removed 5 of 109 rows.** Then the same question, on the same build, with nothing changed but those five rows gone:

> **"I am with you. We are at home, and I am still here with you."**

That is the whole hypothesis tested end to end — prompt-only change produced no effect, purge produced the correct answer, so the contamination was the cause rather than the prompt wording. The matcher is limited to `assistant` rows on purpose: *"Why are you far away from me"* is a real thing Coxy said, and deleting his side of the conversation to make the model behave would be rewriting history rather than cleaning up after a defect. 5 JVM tests, positives taken verbatim from the device. **86/86 JVM tests.**

*A standing lesson worth stating plainly, since this document has now recorded it twice:* **on this setup a bad answer becomes training data for the next bad answer.** Memory is a feedback loop, and any defect that reaches the DB will outlive the fix to the code that produced it. Every behavioural fix from here needs to ask a second question — *what did the broken version already write down?*

**GHOST can speak first — and four things found while proving it (2026-08-19, v0.11.7/versionCode 27).**

*The gap this closes.* Every inference in this app began with something Coxy typed or said. The perception layer fed a `[CONTEXT]` block onto prompts **he** initiated and could never act on its own, so §1's premise — "stop being something that has to be opened, and start being something that's just there" — was not actually built. She perceived continuously and spoke only when spoken to. `TransitionDetector` is the "recent events" half of the §5 context buffer, finally present: two samples of `ContextState` in, a handful of real life events out (arrived home, left home, started moving after real stillness, arrived after travelling, still for 90 minutes). `InitiativePolicy` is the safety surface — off by default, trait gate, never over a call, quiet hours, 45-minute cooldown, six a day, no repeating an observation within three hours, and a user query always outranks it through `EngineGate`.

*This also gives the `initiative` trait a mechanism.* It has been a drift-budgeted, snapshot-versioned slider since Phase 6.3 whose only expression was a sentence in the system prompt — and it could only ever be acted on **inside a reply to him**, which is the one moment initiative is not needed.

*Three properties are load-bearing, and the first is the lesson of v0.11.4 applied before the fact.* **Unprompted turns run cloud-only.** The engine exposes one shared conversation context and a second needs a `:lib` rebuild; that is exactly how `FactExtractor`'s meta-turns entered the model's history and taught it to answer ordinary messages with `FACT: ...`. A cloud call carries its context in the request and leaves no residue, so offline she stays quiet rather than talking into that context. **Only her side is remembered** — storing the synthetic prompt would teach the model that Coxy says `[UNPROMPTED] ...`, the same mechanism one layer up. **The model keeps a veto**, replying `NOTHING` when an event does not warrant a remark, and a veto costs no quota.

*What is still unproven:* generation and delivery. No unprompted remark has ever been produced, because the two gates below it both close — quiet hours during the test window, and the cloud being unreachable. The path from a decision to a notification is code that has never run.

**The 2026-08-12 API key now returns HTTP 401.** `all cloud models failed: HTTP 401: {"error":"Unauthorized"}`. Every reply is coming from the local 1.5B, and because unprompted turns are cloud-only by design, **speaking first cannot work at all until the key is replaced.** The key is present in both places it can live (`ollama_api_key` in `shared_prefs`, and baked into the APK since v0.11.5) — it is being rejected, not missing, so this is a key to re-issue rather than a bug to fix.

Entering the PIN made everything reappear intact — memory DB, staged GGUF, stored key. *A post-deploy "wipe" observed before unlocking is indistinguishable from the real thing, and restoring a backup over it would overwrite live data with an older copy.* Unlock first, then diagnose. The cheap half is a persistent log line, or better, catching the pre-unlock case explicitly and re-starting on `ACTION_USER_UNLOCKED` rather than leaving a boot-start that is known to fail.

The block reports the phone's state, the phone is in his pocket, so the two are never apart — but nothing in the system prompt said so, and a 1.5B will not infer it. **Perception — a guard that had stopped guarding, and two senses that never arrived (2026-08-18, v0.11.6/versionCode 26).** Shipped and verified live. No `:lib` rebuild — the streak holds.

*`hasSignal()` and `toPromptBlock()` had drifted apart, in both directions.* The guard exists so an idle device does not prepend four `unknown` fields to every prompt, and Phase 4.5 quietly broke it. `hasSignal` counted `callState != UNKNOWN`, `nfcEnabled != null`, `inPocket != null` and `nearbyCount >= 0` — but the block deliberately prints call state only when it means "do not speak", NFC only when on, pocket only when true and nearby only above zero. `RadioWatcher` sets call state to IDLE and NFC to true/false the moment it starts, so **from then on every prompt on a running device claimed signal and then rendered nothing but the four unconditional unknowns** — precisely the waste the guard was added to prevent. The other direction was worse and less visible: `gms:off`, `just_picked_up`, a speed, a step rate, a weak signal or a transcript with no timestamp each render a real clause `hasSignal` did not recognise, so with nothing else sensed the block was suppressed and **the model never saw them at all**.

Both are now derived from a single render pass, so the invariant is structural rather than remembered. Also: `micAvailable = false` rendered nothing while counting as signal — "GHOST cannot hear" reached the guard and never reached the model — and now renders `mic:off`, mirroring `camera:off`. That is the only change to what the model reads.

**This is the same shape as every defect in this section, one layer up.** Both halves *were* tested — the omissions are pinned field by field, and so was the signal set. What had no test was the *relationship between them*. The new `hasSignalAgreesWithWhatTheBlockActuallySays` walks 19 representative states and asserts the two agree, re-deriving the answer from the rendered string rather than from the code under test. Three existing assertions turned out to pin the buggy semantics and are inverted with comments saying why.

*`location=` had been dead since Phase 4.* It rendered on every prompt and could never say anything but `unknown`: `handleLocation` took a real GPS fix, pulled `speed` off it for the activity backstop, and hardcoded the bucket behind a "home/away learning is deferred" comment. One of the four unconditional clauses was permanent dead weight. It now buckets against a stored home point (`ACTION_SET_HOME`, from explicit lat/lon or from the last fix; `--ez clear true` removes it). Three decisions made on purpose: **coordinates never enter `ContextState`** — the raw fix is cached on `PerceptionManager` and nowhere else, because everything in `ContextState` is renderable into a prompt and can reach the cloud, the distillation log and the memory DB, so the bucket is the only thing that escapes and it is never logged; **a fix vaguer than the geofence returns `UNKNOWN` rather than a guess**, since a ±500 m reading cannot resolve a 120 m question in either direction and the bedrock says GHOST does not dress a guess up as knowledge; and **haversine in pure Kotlin** rather than `Location.distanceBetween`, keeping the whole decision in the fast JVM tier, with one test pinning the earth radius directly because every other distance test is relative and would pass with a wrong constant.

*Dwell.* "Still" and "still for forty minutes" are different facts and only the first was reachable — every derivative was discarded on the next sensor write. `activity=` now carries how long the bucket has held (`still(100%,42m)`), omitted below a minute and coarse on purpose. The stamp lives in `ContextStore.update` rather than in the writers: three of them change activity, and one that changed it without stamping would leave a duration attached to the *previous* state, which is a confident wrong answer rather than a missing one.

**v0.11.3 — the wake word was never going to work, and now there is a number that says so (2026-08-13).**

Phase 5.2's gate had been open since 2026-08-06 described as "only the human-voice end-to-end confirmation remains" — as if the code were done and only a formality were missing. Attaching an instrument to it showed otherwise on both halves: the trigger logic was wrong, and the model is not fit for the job.

*The measurement, which is the point of this entry.* `KwsScorer` replays recorded clips through the shipped model on the same `AudioRecord` path the live detector listens on. Three 4-second clips of ambient room audio (~-30 dBFS RMS — a normal room, not a silent one), no wake word spoken, scored **peak 0.000, 0.000, 1.000**, and the hit rate is identical (33%) at *every* threshold from 0.30 to 0.90. The output is effectively binary: there is nothing between 0 and 1 for a threshold to sit in, which is why `near-miss` logging never fires. Threshold tuning is not available as a fix.

Then the false-trigger rate, 180 s per setting, ambient audio, no wake word spoken:

| frames | false triggers | rate |
|---|---|---|
| 3 (default) | 6 | ~1 per 30 s |
| 4 | 2 | ~1 per 90 s |
| 5 | 5 | ~1 per 36 s |
| 6 | 2 | ~1 per 90 s |
| 7 | 0 | none in 180 s |
| 10 | 0 | none in 180 s |
| 20 | 0 | none in 180 s |

The 4/5/6 ordering is not monotone because the room is not a controlled environment — read these as an order of magnitude, not a rate. **The peak was 1.000 in every single 10-second window of every configuration.** The model is not occasionally spiking; it is saturated at maximum confidence on ordinary room noise, and only the consecutive-frame requirement keeps that from becoming a trigger.

Now cross that with the geometry, which is what makes the verdict decisive. The window is 1 s advancing 50 ms, so a phrase lasting D seconds sits fully inside the window for only `(1 − D)/0.05 + 1` frames — about 11 at 0.5 s, 7 at 0.7 s, 4 at 0.8 s. A naturally spoken "Hey Ghost" cannot produce many more than ~7 consecutive frames, and ~7 is exactly where the false triggers stop. **The quiet settings and the wakeable settings do not overlap.** No threshold and no debounce makes this model both silent at idle and reliable on a real voice.

So the conclusion this document has been missing for a week: **the wake word is a training problem, not a tuning problem, and it could never have passed its gate.** `hey_ghost.tflite` is 100% macOS `say` synthesis; on real room audio it saturates instead of discriminating. Retraining on real clips (`tools/kws_gate.sh record` → `train_hey_ghost_kws.py --real-data`) is now the blocking item, **ahead of** the live gate rather than after it. Note `tensorflow` is not currently installed on the Mac, which that script needs.

`DEFAULT_FRAMES` stays at 3 deliberately — not because 3 is quiet, but because it is the most permissive setting measured and therefore the most *diagnostic*: if the wake word fails to fire at 3 on a real voice, the model is conclusively the problem. For a quiet mic in the meantime, `./tools/kws_gate.sh tune 0.80 7`, or turn the mic off.

*Trigger hardening.* The decision was three lines inlined in the audio loop, which is why it had never been tested. Extracted into `WakeTrigger`: a **consecutive-frame debounce** (a real utterance holds the 1 s window across ~20 overlapping frames; a transient spikes one), plus a cooldown that is re-armed when the recognizer hands the mic back, so a long command cannot burn the cooldown and let the detector re-fire on its first frame. 12 JVM tests pin it.

The debounce helps and is worth keeping, but it does **not** rescue this model — see the soak below. The first 20 seconds of observation showed zero triggers and that looked like a fix; a longer run showed otherwise, which is the same "the gate was weaker than it read" mistake this document keeps recording. The honest measurement is the one below, not the first encouraging one.

*Four defects fixed alongside it, all in the mic path:*
- **The one-shot recognizer retry documented in Phase 5.2 had never run.** `commandRecognizer` was assigned *before* `startListening`, so the retry's own `if (commandRecognizer != null) bail` guard was always true on the failure path. Every recognizer bind failure was a silently dropped wake word. The handle is now published only after the recognizer is actually listening.
- **Every wake reloaded the TFLite model.** `resumeKws` called `detector.init(ctx)` purely to clear the audio ring — a full interpreter teardown and rebuild on the mic thread, with a source comment that guessed "re-init is cheap". It is not. `WakeWordDetector.reset()` clears the ring and leaves the model loaded; an instrumented test pins that the ring is empty afterwards *and* that the detector still scores.
- **Two different units shared one field.** `SpeechRecognizer.onRmsChanged` (its own ~-2..10 scale) and the `AudioRecord` loop (real dBFS, -100..0) both wrote `ContextState.audioLevelDb`, which renders as `mic=voice(NdB)` — in the status line and in the `[CONTEXT]` block the model reads. The `AudioRecord` path now owns the field.
- **A revoked `RECORD_AUDIO` leaked the mic.** `ERROR_INSUFFICIENT_PERMISSIONS` cleared `isRunning` but left `AudioRecord` open and recording with nothing draining it; it now tears the pipeline down.

*Tunable at runtime, because the alternative was absurd.* Threshold and frame count moved to DataStore behind `ACTION_SET_KWS_TUNING`. Sweeping a baked-in constant meant a rebuild + priv-app deploy + reboot per step (~20 min), on a deploy flow that has wiped app data three times. It is now one shell command, applied to the running pipeline without dropping the audio stream — verified live.

*Observability.* `MicListener` logs a 10-second rolling peak probability and flags near-misses (≥60% of threshold). "It didn't wake up" is now answerable from logcat: a high peak that never fired is a tuning problem, a peak of 0.05 is a training problem. `tools/kws_gate.sh` drives the whole loop — `record`, `score`, `tune`, `watch`, `pull`.

*Verification:* **41/41 JVM tests** (29 existing + 12 new `WakeTriggerTest`) and **3/3 `WakeWordDetectorTest` on RMX3760**, including the new `reset()` test. The full record → score → tune → pull loop was exercised on device: 3 clips captured (64,000 samples each, valid 16 kHz mono 16-bit WAV), scored, tuning applied live, clips pulled to `tools/kws_data/real/` — which now exists for the first time, closing the v0.9.3 note that the capture capability was "built, not yet used". **v0.11.x — Obsidian UI, and finding out why the replies were poor (2026-08-12).**

*The brain.* The replies had been noticeably weak, and the assumption was that routing needed changing to put the cloud first. It did not: `CloudRouter` has always tried cloud first with the local engine only as a fallback, and `cloud_enabled` already defaults to true. The real cause was that **no API key was ever stored** — `shared_prefs/ghost_cloud_key.xml` holds only the two Tink keyset entries, with no encrypted value beside them; the file exists purely because opening the Cloud screen initialises `EncryptedSharedPreferences`. So `getKey()` returned null and every query since the 2026-08-12 wipe took the local path. Three things had made that invisible, all now fixed:
- The router logged one line, "cloud disabled or no key", for two different conditions. Each is distinct now, and the missing-key case logs at warn with how to store one.
- Nothing on screen said which brain answered. `CloudRouter.lastBrain` is published and the chat shows it as a chip — `brain: cloud · qwen3.5`, or `brain: local · no API key` / `· offline` / `· cloud off` / `· cloud failed`. A local answer now says *why* it was local.
- Offline fallback waited out a 15s connect timeout per model in the chain, up to 30s, before falling back. A connectivity check short-circuits that to an immediate local answer (`ACCESS_NETWORK_STATE`, read-only).

`qwen3.5` is now first in the model chain, with the gpt-oss entries kept behind it deliberately: Ollama Cloud names normally carry a `-cloud` suffix, so a bare `qwen3.5` may not resolve, and until that is confirmed the fallbacks are what stand between a wrong name and a silent drop to the 1.5B. `CloudClient.lastModelUsed` now reports which model actually answered — previously the distillation log recorded `chain[0]` regardless, mislabelling every row whenever the primary failed over.

*The UI.* The app was still the stock Android Studio template. It was rebuilt against a Stitch design system ("Obsidian Futurism"), adapted on two points: a true `#000000` base rather than the system's `#101415`, because this is an AMOLED panel and black pixels are off pixels; and soft-technical corners (12dp cards, 10dp buttons) rather than pill-round. Three screens behind a bottom nav — **Chat** (conversation, live sensor chips, composer), **Live** (a lit sphere that rests, listens, thinks and speaks, driven by `ContextStore` and `EngineGate` rather than a timer), and **System** (every configuration; the other two screens carry none). An earlier attempt at this (v0.10.x, a drifting aurora behind glass panels) was rejected and replaced. **Phase 4.5 — the rest of the device's senses (2026-08-12, v0.9.7/versionCode 16).** GHOST was registering 3 of the 36 sensor types the RMX3760 exposes, and its own system prompt described states it could not sense: "in Coxy's pocket, on his desk, face-up in the dark beside him" were inferred or invisible. Now 12 registrations, confirmed live in `sensorservice`:
- **Posture** from the vendor `com.spreadtrum.face_up_down` sensor, with pitch/roll off the rotation vector as fallback.
- **In-pocket** from `com.spreadtrum.pocket_mode` (previously proxied by `proximity=NEAR`); like proximity it forces the light bucket to DARK.
- **Compass heading** (8-point) from the fused rotation vector.
- **Motion** from the one-shot stationary/motion/significant-motion triggers.
- **Pick-up and tilt** → `just_picked_up`.
- **Step detector** alongside the counter, so the rate does not decay mid-stride.
- **`BleScanner`** — duty-cycled low-power scans (8s every 5min) on a radio already powered on. Reports a *count* of nearby devices and names only devices already **bonded** to this phone; a stranger's device contributes to the count and nothing else, and no address is stored, persisted or sent.
- **`RadioWatcher`** — call state (the clearest "do not start talking" signal), signal level, network generation, NFC on/off. State only: no numbers, contacts or messages.

Deliberately excluded, with reasons in the code: raw gyroscope/accelerometer/magnetometer streams (the rotation vector *is* the HAL's fusion of those three; registering them on top would wake the CPU at up to 100 Hz to re-derive what already arrives); biometrics as context (fingerprint and face are authentication APIs, not readable sensors — there is no honest context field to fill); and NFC tag reading (needs a physical tap into a foreground activity's reader mode, which a background daemon cannot do).

Every new field is omitted from `[CONTEXT]` unless it carries information, so an idle phone costs exactly as many tokens as before; `ContextStateTest` pins that rule field by field. Two platform details worth keeping: the one-shot sensors do not work through `registerListener` at all and need `requestTriggerSensor` with a manual re-arm, and pick-up/tilt have no public `Sensor.TYPE_*` constants so they are resolved by their platform type numbers.

**A wake loop this introduced, caught on-device.** The first live run showed stationary-detect cancelling and re-arming every ~5s on a phone sitting still, because `onTrigger` re-armed the sensor that had just fired *as well as* its opposite — and a stationary phone re-triggers stationary-detect the instant it is re-armed. "Cheap and event-driven" had become a 5-second wake loop, exactly the cost this tier was chosen to avoid. The pair is a state machine: each now arms only its opposite, and only stationary-detect is armed at startup.

**BLE nearby-sensing is wired and permitted but reports nothing**, because Bluetooth is off (`enabled: false, state: BLE_ON` — the radio is up for system scanning but the adapter is off to apps). It stands down and stays silent rather than reporting a fake zero.

**v0.9.5 — Tier 1 hardening, and the deploy that forced a backup step (2026-08-12).** A full audit of the app against this document found two "gate passed" claims that were false and a set of concurrency defects in the typed path. Six commits in the app repo:
- **The action layer had never been wired to the model.** `GhostPrompts.BASE_ROLE` contained `{{ACTION_LIST}}` and `{{PERSONALITY_BLOCK}}` as literal text — `buildSystemPrompt` only concatenated, nothing ever called `.replace()`. - **`EngineGate` was a check-then-set, not a gate.** Three callers on three threads (main, `Dispatchers.Default`, `GlobalScope`) each ran `if (busy) return; busy = true`, so two could observe false and both drive the single-threaded engine. Now an `AtomicBoolean` with `tryAcquire()`/`release()`. Measured over 2000 rounds of 8 racing threads: the old pattern admitted two callers in 2 rounds, the CAS in none — rare enough to read as random conversation corruption rather than a bug.

**v0.9.1 — mic loop fix + live-control toggle (Phase 5.1→5.2 interim).**
- **Problem:** driving `SpeechRecognizer` continuously for wake-word detection produced an audible HAL on/off blip loop even in silence, because the recognizer restarts after every `NO_MATCH`/error.
- **Fix:** the continuous mic is now gated by a runtime `DataStore` preference (`GhostPrefs.KEY_MIC_ENABLED`, default `false`). `MicListener.start()` respects the preference; a new `MicListener.setEnabled(enabled)` toggles the recognizer on/off without killing the service. The restart cadence was also slowed (`RESTART_DELAY_MS=1200L`, `BACKOFF_DELAY_MS=5000L`, `MAX_FAST_RESTARTS=10`).
- **UI control:** `MainActivity` has a new 🎤 Mic button (`btn_mic`) that toggles the preference and calls `micListener.setEnabled(next)`; the button label tracks the current state.
- **Remote control:** `GhostService` handles `ACTION_TOGGLE_MIC` (`com.coxy.ghost.action.TOGGLE_MIC`) so the mic can be toggled via root shell: `adb shell su -c "am startservice -a com.coxy.ghost.action.TOGGLE_MIC -n com.coxy.ghost/.GhostService"`.
- **Context state:** `MicState.OFF` was added; when the mic is disabled the `[CONTEXT]` block emits `mic:off` and the status line shows `mic:off`, so it's obvious when GHOST is not listening.
- **Verification:** 40/40 instrumented tests passed after the mic changes. Live on-device: the Magisk module was updated to the new build, the device rebooted, the app/package manager issue (stuck `stopped=true` after replacing a system app) was cleared by editing `package-restrictions.xml`, and `MainActivity` now launches from `adb`. Toggling the mic via the service action produced `MicListener: starting continuous mic perception` followed by `MicListener: pausing mic (disabled by user)`, confirming the control path and silencing the loop when the mic is off.
- **Remaining:** the true Phase 5.2 goal is a dormant keyword-spotter that wakes only on "Hey Ghost" without any always-on full STT. This interim toggle removes the looping noise immediately and gives an explicit "Live mode" path until a lightweight KWS is built.

**v0.9.2 — lightweight "Hey Ghost" keyword spotter (Phase 5.2, in progress).**
- **Design:** the always-on listener is now a single `AudioRecord` instance at 16 kHz mono 16-bit, feeding a tiny TFLite model `assets/hey_ghost.tflite` that ingests a 1-second waveform and emits wake-word logits. The graph includes its own STFT spectrogram, so Kotlin only copies raw PCM into a float buffer. A sliding 1-second ring buffer means inference runs on every 50 ms chunk; when the softmax probability crosses `0.80f`, a transient `SpeechRecognizer` session starts, captures the command, strips the wake word, and dispatches it through the existing voice-command pipeline. After the command (or silence), the recognizer is destroyed and the quiet `AudioRecord` stream resumes.
- **Files:** `WakeWordDetector.kt` interface; `TfliteWakeWordDetector.kt` loads the model, maintains the ring buffer, and runs `Interpreter` on the mic thread; `MicListener.kt` rewritten to own the `AudioRecord` loop and the command-capture state machine; `WakeWordDetectorTest.kt` instrumented test feeds positive and negative WAV assets.
- **Training:** `tools/train_hey_ghost_kws.py` downloads TensorFlow `mini_speech_commands` for negatives, synthesises ~2,400 positive "Hey Ghost" clips via macOS `say` + pitch/speed/noise augmentation, trains a small Conv2D on spectrograms, and exports an end-to-end waveform-to-logits TFLite model to `app/src/main/assets/hey_ghost.tflite`. Test clips are copied to `app/src/androidTest/assets/`.
- **Plumbing preserved:** the existing `ContextStore` voice-command path, `EngineGate`, `GhostService.runVoiceCommand`, cloud routing, and action execution are unchanged; `MicListener` still writes `voiceCommand`/`voiceCommandSeq` and streams the reply via `voiceResponse`.
- **Status (corrected 2026-08-12):** training is **done** — `app/src/main/assets/hey_ghost.tflite` (1,635,928 bytes) was generated 2026-08-07 and ships in the APK; `WakeWordDetectorTest` passes on RMX3760 as part of the 59/59 suite. The earlier "training in progress" note here contradicted §7 Phase 5.2 in this same document, which already recorded the asset as deployed. The only thing still outstanding is the **live human-voice gate**: "Hey Ghost, <command>" → response, with a silent mic when idle.

**v0.9.3 — real-voice KWS capture path (2026-08-11).** The spotter is trained purely on synthetic macOS `say` positives, which is a known weak point for a keyword model that has to fire on one specific human voice. `KwsSampleRecorder` records through the **same `AudioRecord` MIC path the detector uses** — ALSA-level `tinycap` bypasses the HAL noise reduction and so produces clips that do not match what the detector actually hears. Driven by `ACTION_CAPTURE_KWS` (`GhostService`), with `tools/record_kws_samples.sh` on the Mac side. `tools/train_hey_ghost_kws.py` gained `load_real_clips()` plus `--real-data`, `--real-oversample` and `--real-only`. **Not yet used:** `tools/kws_data/real/` does not exist — the capability is built, no real clips have been collected, and the shipped model is still 100% synthetic. Also added `tools/deploy_system_app.sh`, which replaces the by-hand APK/native-lib swap described in the Phase 7 and Phase 8 entries below.

**v0.9.4 — model staging without the UI (2026-08-11).** When the app's uid changed on 2026-08-09 the DataStore was wiped, and GHOST ran from then on with no local model and no way back except tapping through the SAF picker by hand — the daemon perceived but could not reason offline, silently removing the fallback half of the Phase 8 cloud/local story. `ACTION_SET_MODEL_PATH` (`--es path <gguf>`) persists the path and reloads the engine from a root shell, re-arming the once-only `setSystemPrompt` guard the same way `reloadModelForPersonality` does. This is the path that recovered the device after the v0.9.5 deploy wipe.
